# 本地业务数据库健康检查

版本：1.2.68

每次本机检查增加 database.sqlite，后台及 Linux 菜单沿用同一份扫描报告。只核对 Compose project=appgog/service=appgog 的完整容器 ID、部署角色、工作目录和 appgog_appgog-db 本地数据卷归属。独立打包节点没有授权数据库，此项明确显示不适用；一体和授权节点必须有固定 appgog.sqlite 数据库。

代理以不跟随链接的只读描述符复制数据库及 WAL 到权限 700 的私有临时目录，文件权限 600。不打开线上 SQLite 连接，不读取客户记录，不复制线上 shm，不执行线上 checkpoint、VACUUM、恢复或删除。前后核对文件身份和容器/数据卷归属；源文件正在变化、链接/特殊文件、硬链接、数据库缺失、非空回滚日志或总大小超过 128 MiB 时结果未知。

在独立 Python 子进程的临时副本上运行 SQLite integrity_check(100)，只返回固定状态，不返回 SQL、表名、客户记录、路径或数据库错误文本。关闭扩展加载、关闭 trusted_schema、开启 query_only，缓存上限 8 MiB；Linux 子进程内存上限 256 MiB、CPU 上限 8 秒，父进程 12 秒超时。副本产生的 WAL 索引仅在私有临时目录，退出自动清理。故障、超时和不支持的数据库格式均不能变绿。

SQLite 结构损坏或空数据库显示 finding，保留原始业务数据并告警。数据库结果未知或损坏会阻止事故容器解封；查杀中心不擅自删除、重建数据库或恢复覆盖客户数据。原有程序自动隔离策略不因单独数据库告警而扩大。

结构检查可以使用 WAL 中已提交页面，但不证明每条日志帧、业务记录真实性、授权是否合法或无 SQL 注入。合法 SQL 对业务记录的恶意修改可能通过结构检查；业务权限、审计及独立备份仍须分别保护。持续繁忙写入期间可显示未知，不能为获得正常状态绕过快照一致性核对。宿主 root 失守仍须干净主机重建。

单元验收使用真实 SQLite 引擎和 WAL，Docker 归属在单元测试中明确模拟；独立 Linux Docker 验收使用真实标记容器和真实本地数据库卷，执行完保留/核对数据并清理测试资源。这两种证据不能等同生产数据库或全机容灾验收。
